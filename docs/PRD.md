# ТЗ: интерактивный фронтенд-прототип платформы онлайн-репетиторства

> **Формат:** кликабельное веб-приложение без бэкенда.  
> **Цель:** продемонстрировать UX/UI и полные пользовательские сценарии для согласования продукта.  
> **Основа:** `TZ_Online_Repetitorstvo_MVP_v1_1.docx` (20.10.2026) и `BPMN_Online_Repetitorstvo_Interactive.html` (P-01—P-06).  
> **Статус:** спецификация реализации прототипа; детали поведения на моковых данных ниже — **демонстрационные допущения**, а не новые утверждённые бизнес-правила.

## 1. Главное требование

Сделать **полностью кликабельный responsive frontend**, который визуально и по пользовательским сценариям выглядит как работающий сервис. **Бэкенд, настоящая БД, реальные платежи, отправка SMS/e-mail, Zoom API и серверная авторизация НЕ нужны.**

- Всё содержимое: **локальные mock-данные**; изменения — в состоянии приложения (опционально `localStorage` для сохранения при перезагрузке).
- Все основные действия должны иметь видимый результат: изменения статуса, сообщения, переходы, обновление чисел, календаря и списков.
- Никаких пустых кнопок, бессмысленных ссылок, бесконечных загрузок и неработающих основных форм.
- В интерфейсе помечать искусственные внешние действия: **«Демо-оплата»**, **«Демо-уведомление»**, **«Тестовая Zoom-ссылка»**.
- При обновлении страницы пользователь может продолжить демо; предусмотреть **«Сбросить демо-данные»**.
- Данные детей — только вымышленные.

## 2. Технические рамки

**Рекомендуемый стек для прототипа (не задан исходными документами):** React + TypeScript + Vite, Tailwind CSS, React Router, иконки Lucide; основная UI-библиотека — **shadcn/ui** (на базе Radix UI), иконки Lucide. Если проект уже существует, адаптировать рекомендации к его стеку без ненужной миграции.

- Только клиентский рендеринг; не создавать backend, API-сервер, БД, миграции, платежные/почтовые ключи.
- Моковые сущности вынести в `src/mocks/`, бизнес-операции — в `src/services/mock*` или аналогичный слой, чтобы позднее заменить реализациями API.
- Локальное хранилище с версией схемы; для первого открытия — seed данных.
- Навигация работает через маршруты; обновление страницы сохраняет корректное отображение маршрута.
- Desktop-first для кабинета модератора и mobile-friendly для родителя/ученика; ориентиры 1440px, 768px, 390px.
- Язык интерфейса в прототипе — **русский**; данные поддерживают поле «язык обучения» (например, русский/казахский). Мультиязычный UI не требуется без отдельного согласования.

## 3. Роли и переключение сценариев

**Гость:** лендинг, каталог пакетов, каталог проверенных преподавателей.  
**Родитель:** дети, пакеты, покупка и продление, перераспределение, расписание, обратная связь и отзывы.  
**Ученик:** расписание, карточка урока/Zoom, история, обратная связь и оценка преподавателя.  
**Учитель:** анкета, расписание, состав групп, посещаемость, отчёты.  
**Модератор:** проверка учителей, пакеты, группы, расписание, подтверждение отчётов, аналитика.  
**Администратор:** демонстрационные справочники/роли/журнал действий (упрощённо).

**Демо-вход вместо авторизации:** на `/demo` показать выбор роли и заранее подготовленного профиля; переключатель роли в шапке или меню. Для демонстрации регистрации есть отдельные формы родителя и ученика; ввод создаёт локальную запись. Никакие пароли реально не проверяются и не должны собираться как настоящие учетные данные. Один пользователь может обладать несколькими ролями; отображение переключателя ролей — допустимый сценарий.

## 5. Ключевые UI-компоненты

- Общие: адаптивная шапка, боковое меню кабинета, breadcrumbs, карточки, таблицы, фильтры, теги статусов, модальные окна, wizard, toast-уведомления, skeleton/empty/error states.
- Каталог: карточки пакетов и преподавателей, поиск и фильтры, детальные страницы.
- Пакеты: визуальный распределитель занятий между разрешёнными предметами, счётчик **«назначено X из N»**, валидация.
- Квоты: понятная разбивка **куплено / списано / зарезервировано / свободно / истекло** и привязка к заказу и ребёнку.
- Календарь: переключение видов, создание занятия, детали слота, статусы, список участников.
- Учитель: матрица посещаемости с индивидуальной обратной связью по каждому ученику.
- Модератор: очереди на проверку, подтверждение/отклонение с комментарием.
- Аналитика: KPI-карточки, таблицы, фильтры, раскрытие до конкретного заказа, ученика и занятия.

## 6. Интерактивные сценарии — обязательны

### P-01. Покупка пакета
1. Гость открывает каталог и выбирает пакет.
2. Распределяет **ровно N** уроков между разрешёнными предметами; выбор класса, языка, желаемого учителя.
3. Добавляет/выбирает ребёнка, заполняет данные родителя (демо).
4. Ставит галочку акцепта оферты; кнопка оплаты до этого недоступна.
5. Нажимает «Оплатить (демо)». Показать переключение **«Успешно / Отклонено»** как демо-симуляцию.
6. Успех → новый `paid` заказ, начисленные квоты, экран подтверждения, обновление кабинета. Ошибка → `unpaid`, без квот, возможность повторить оплату.
7. Повторное нажатие/симуляция повторного webhook **не удваивает квоты**.

### P-02. Проверка преподавателя
1. В демо-режиме модератор назначает пользователю роль учителя.
2. Учитель заполняет анкету: ФИО, фото-заглушка, предметы, классы, языки, стаж, категория, школа, биография.
3. Отправляет на проверку: `pending_review`.
4. Модератор возвращает с замечанием → `needs_revision`, либо одобряет → `published`.
5. Опубликованный профиль виден в каталоге; непроверенный и снятый — нет.

### P-03. Планирование группового занятия
1. Модератор выбирает дату, время, предмет, класс, язык и пакет/тип занятия.
2. Выбирает проверенного преподавателя, подходящую группу и учеников с **оплаченными свободными квотами**.
3. Вставляет тестовую Zoom-ссылку.
4. Валидаторы: лимит группы; соответствие предмета, класса и языка; наличие квоты; отсутствие пересечений расписания ученика и учителя; наличие ссылки.
5. Ошибка → блокировать публикацию и показывать причину рядом с полем.
6. Успех → урок `scheduled`, по одной зарезервированной квоте на каждого участника; урок появляется у учителя, ученика и родителя.
7. Перенос/отмена (демо) обновляют календарь и резервы; показать уведомление внутри приложения.

### P-04. Проведение и закрытие занятия
1. Учитель открывает прошедший урок и вводит тему, фактическое время, факт проведения, посещаемость и заметку **для каждого ребёнка**.
2. «Отправить отчёт» → `pending_approval`.
3. Модератор либо возвращает с замечанием, либо подтверждает.
4. До подтверждения квоты **только в резерве**; финального списания нет.
5. После подтверждения → `closed` и отдельный результат по каждому участнику: списать либо восстановить резерв согласно настроенному **демо-правилу пропусков**.
6. Родитель/ученик видит опубликованную обратную связь и может оставить отзыв **только по подтверждённому участию**.
7. Повторное подтверждение не списывает квоты повторно.

> **Важно:** конкретная политика пропусков в исходном документе не утверждена. Для прототипа в панели демо-настроек дать наглядный выбор: «пропуск → вернуть резерв» / «пропуск → списать»; не позиционировать ни один вариант как финальную политику.

### P-05. Перераспределение предметов
1. Родитель открывает оплаченный заказ и видит по каждому предмету: куплено, списано, зарезервировано, свободно.
2. Меняет распределение **только свободных** занятий, не трогая проведённые и забронированные.
3. Проверка: сумма сохранена; предмет разрешён пакетом; коммерческая равноценность.
4. Валидно → обновить показатели и локальный журнал изменений; невалидно → показать причину и не менять данные.
5. Для разных цен предметов использовать демо-режим **«обмен запрещён без согласованного тарифа»**, явно помеченный как допущение.

### P-06. Продление пакета
1. Родитель нажимает «Продлить» и настраивает **новую** покупку.
2. Принимает актуальную оферту и проходит демо-оплату.
3. Успех создаёт **новый заказ с отдельными квотами**, не изменяя прошлый заказ.
4. На экране доступны общий остаток по ребёнку и детализация по каждому заказу.
5. При неуспехе новые квоты не создаются.

## 7. Минимальные mock-данные

Создать достаточно данных для всех экранов и состояний:

- 4–6 пакетов с разной стоимостью, числом уроков, предметами, длительностью и лимитом группы.
- 8–12 учителей с разными предметами/языками/статусами; минимум один `pending_review`, один `needs_revision`, один `published`, один `unpublished`.
- 2–3 родителя, 4–6 учеников (с разными классами и языками обучения).
- 6–10 групп и 15–25 уроков: будущие, прошедшие, ожидающие отчёта, на проверке, закрытые, отменённые.
- Заказы: оплаченный, неоплаченный, с частично потраченными квотами, с полностью зарезервированными квотами, продлённый.
- Отзывы и обратная связь с разными оценками.
- Для P-03 предусмотреть слот с конфликтом и ученика без свободной квоты.

**Базовые клиентские типы:** `User`, `Role`, `ParentProfile`, `StudentProfile`, `TeacherProfile`, `TeacherCompetency`, `Package`, `PackageVersion`, `Order`, `OrderItem`, `OfferAcceptance`, `Payment`, `Group`, `GroupMember`, `Lesson`, `LessonParticipant`, `QuotaTransaction`, `LessonFeedback`, `TeacherReview`, `Notification`, `AuditLog`.

Не обязательно воспроизводить серверную схему БД. Достаточно типизированных объектов и связей по ID. Важно сохранить трассировку **заказ → предметная квота → участие ребёнка → групповой урок**.

## 8. Локальные правила состояния

- Групповой урок = **один** `Lesson`, а каждый участвующий ребёнок = отдельный `LessonParticipant`.
- Квоты учитывать на уровне **ученик + заказ + предмет**; не вести один общий счётчик, который невозможно проверить.
- Разделять `available`, `reserved`, `consumed`, `expired` (и при необходимости corrections/refunds). Простые отображаемые агрегаты вычислять из локальных данных.
- `reserve`: уменьшает свободные и увеличивает резерв только для конкретного ученика и заказа.
- `confirm`: переводит резерв в списание (либо восстанавливает по выбранному демо-правилу).
- `cancel`: освобождает резерв и убирает участие из активного расписания.
- `reallocate`: меняет только свободные квоты между разрешёнными предметами, сохраняет суммарную величину.
- `renew`: создаёт новый заказ, а не перезаписывает существующий.
- Операции «оплата», «резерв», «подтверждение» должны быть идемпотентны и в локальной модели.
- Вести локальный `auditLog` основных действий и показывать его в упрощённом интерфейсе.
- Отображать понятные пустые состояния и демонстрационные ошибки, если нет данных или не проходит проверка.

## 9. Дизайн и UX

- Стиль: современная образовательная платформа, светлый фон, чистые карточки, аккуратные акценты, крупные читаемые заголовки. **Конкретный брендбук в исходниках не указан**, цвета/шрифты можно выбрать для демо.
- Для родителей — понятные действия, остатки, расписание и статус покупки.
- Для ученика — минимум сложных терминов, фокус на ближайшем уроке и кнопке перехода к Zoom.
- Для учителя — быстрые действия с отчетом и посещаемостью.
- Для модератора — плотный рабочий интерфейс, таблицы, фильтры, массовый обзор задач.
- У каждого действия: loading (короткая имитация), success/error, возможность закрыть диалог; опасные действия подтверждать.
- Формы с валидацией и текстовыми ошибками; навигация с клавиатуры, видимый focus, контрастные элементы управления.
- Не использовать реальные фотографии детей и личные данные.

## 10. Что не делать

- Никакого backend, Supabase/Firebase, реального OAuth, JWT, сетевых API или админ-сервера.
- Никакой интеграции с банками, QR, SMS, почтовым сервисом или Zoom API.
- Не реализовывать видеоуроки внутри платформы: достаточно кнопки «Открыть тестовую Zoom-ссылку».
- Не разрабатывать настоящий биллинг, бухгалтерию, юридически значимое согласие, полноценные политики обработки персональных данных.
- Не тратить время на production-grade защиту и масштабирование; но UI не должен вводить в заблуждение о реальных платежах или авторизации.
- Не добавлять индивидуальные занятия — в исходном MVP **только групповые**.

## 11. Порядок разработки прототипа

1. **Основа UI:** layout, навигация, переключение ролей, типы и seed данных.
2. **Публичная зона + покупка:** лендинг, пакеты, учителя, checkout, локальные заказы.
3. **Кабинеты:** родитель/ученик/учитель/модератор, таблицы и календари.
4. **Сценарии работы:** модерация учителей, создание урока, резерв, отчёт, подтверждение, перераспределение, продление.
5. **Полировка:** аналитика, уведомления, пустые состояния, адаптивность, демо-сброс, прогон сценариев.

## 12. Критерии готовности (Acceptance / DoD)

- [ ] Можно открыть сайт и без регистрации перейти в каждую роль через демо-переключатель.
- [ ] Публичные страницы заполнены моковыми данными; фильтры работают.
- [ ] Можно купить пакет, увидеть новый заказ и правильные предметные квоты.
- [ ] Нельзя распределить больше/меньше занятий, чем предусмотрено пакетом.
- [ ] Неуспешная демо-оплата не начисляет квоты, повтор успешной — не дублирует.
- [ ] Проверка учителя изменяет статус и публичную видимость.
- [ ] Модератор может создать групповое занятие; конфликты, вместимость и нехватка квот блокируют публикацию.
- [ ] После публикации урок появляется в календарях задействованных ролей; квоты отмечены резервом.
- [ ] Учитель может отправить индивидуальный отчет по детям; модератор — вернуть или утвердить.

### 15.2. Дизайн-токены (стартовое предложение)

Эти цвета **демонстрационные** и могут быть заменены после согласования фирменного стиля. Настроить их как семантические CSS-переменные и привязать к теме shadcn/ui; не размножать HEX по компонентам.

```css
:root {
  --brand-primary: #4f46e5;
  --brand-secondary: #0ea5e9;
  --app-background: #f8fafc;
  --surface: #ffffff;
  --text-primary: #0f172a;
  --text-secondary: #64748b;
  --border-default: #e2e8f0;
  --radius-sm: 8px;
  --radius-md: 12px;
  --radius-lg: 16px;
}
```

- **Типографика:** Inter (или системный sans-serif fallback); единая шкала заголовков, текстов, подписей и числовых метрик.
- **Отступы:** шкала на основе 4/8 px; согласованное расстояние в карточках, таблицах и формах.
- **Сетка:** responsive layout; desktop — боковая навигация в кабинетах, mobile — сворачиваемое меню/Sheet.
- **Карточки:** светлые поверхности, аккуратная граница, мягкая тень там, где она усиливает иерархию.
- **Статусы:** `draft`, `pending`, `approved`, `published`, `scheduled`, `closed`, `cancelled`, `paid`, `unpaid` — через **семантические** Badge (цвет + текст/иконка), а не только цвет.
- **Состояния:** `hover`, `active`, `focus-visible`, `disabled`, `loading`, `empty`, `error`, `success` для всех важных компонентов.
- **Доступность:** читаемая контрастность, клавиатурная навигация, подписи к полям, видимый фокус, корректные `aria-label` в иконках и диалогах.
- **Язык UI:** русский; примеры предметов и языков обучения должны соответствовать моковым данным проекта.
